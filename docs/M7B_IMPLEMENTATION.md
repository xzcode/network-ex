# M7b controlled Ethernet TAP overlay (2026-11-26)

Version 0.7.1-dev-m7. Linux real Layer-2 TAP mode for IPv4/ARP is available separately from the original Layer-3 TUN. It is not a general transparent Ethernet bridge or a physical LAN bridge.

## Management and opt-in
SQLite schema v6 adds network Ethernet-mode policy and signed device Ethernet opt-in. Administrator GET/PUT /api/v1/networks/{id}/ethernet, with {"enabled":true}. Network owners can read. The Web admin includes a mode control and interruption warning. Enabling is refused if subnet routes or exit grants exist. Conversely, creating subnet routes/exit grants is rejected while Ethernet mode is enabled. Mode changes increment network revision and clear previous mode announcements.
Run managed-run or daemon with -layer2 (Linux only; daemon default profile). The local administrator must select the same mode as the network; mismatches fail closed with HTTP 426. Pending devices do not establish interfaces. Only approved, authorized peers with fresh matching opt-in join Ethernet mode. The independent -game-discovery flag opts in to previously configured UDP discovery rules; ARP and IPv4 unicast do not require this flag. For a network with approved UDP broadcast or multicast, use both flags. Do not run both TAP and TUN on the same address space. Existing route and underlay conflict checks protect the complete subnet, and setup refuses conflicting routes rather than replacing them.

## Data plane
A Linux TAP (IFF_TAP, IFF_NO_PI, exclusive interface) is configured with an assigned overlay IPv4 address and actual /24–/28 prefix; the locally administered unicast MAC is 02:4e plus the four assigned IPv4 octets. Physical MACs are not used. Kernel ARP resolves authorized peers normally. TAP MTU 1200, per-frame max 1214 including Ethernet header. IPv6 is disabled on the new TAP where supported and frames are rejected by the codec. The enclosing WireGuard IPv4 packet MTU remains 1280.
Validated Ethernet frames are encapsulated in per-peer IPv4 packets using internal protocol 252 and carried by the existing authenticated WireGuard direct/ICE or WSS relay path. Receiver verifies exact source IP/MAC ownership and destination before delivering the frame locally. IPv4/ARP only; no VLAN, arbitrary EtherTypes, DHCP, IPv6, physical NIC bridging, MAC learning, unknown-unicast flooding or L2 transit. ARP requests are sent only to their authorized target; replies must match the assigned hardware and IP addresses. IPv4 unicast is bound to the exact peer MAC/IP and existing bidirectional service ACL. Broadcast/multicast requires explicit M7 destination/UDP port allowlist and local discovery opt-in on both sides. Broadcast frame delivery has TTL reduced to one; no recursive forwarding. ARP/group rate: 32 originals/s, 128 fanout/s, 128 aggregate inbound/s and 32 inbound per peer/s (initial limits; bursts equal rates). Pending expansion bounded by approved peer count (max 64). Spoofed source, unauthorized peer/port, unknown MAC, unsupported EtherType and nested experimental IP packets rejected. The ordinary TUN guard also rejects internal Ethernet envelope protocol.
Status reports real MAC and per-tunnel-generation sent/received/dropped/ARP/group counts. Vue overview renders them. Native desktop, Windows/macOS TAP runtime are not implemented; non-Linux refuses Ethernet mode. Existing Linux/Windows/macOS Agent builds continue to support prior L3 capabilities.

## Verified
Initial isolated Linux integration test exited 0: three managed Agents, local Ethernet opt-in enforcement; A-B ICE direct and A-C WSS relay (physical UDP blocked on C); actual Linux link type ether, /24 and MTU 1200, deterministic MACs, kernel ARP neighbor table; TCP/UDP echoes; directed broadcast 10.88.0.255, scoped multicast 239.88.0.7 and limited broadcast 255.255.255.255 all discover both real socket responders; unapproved port denied; policy withdrawal preserves IPv4 unicast/ARP; graceful TAP and connected route removal. Live counters were observed on all three nodes. This is a real network/socket room-discovery fixture, not a named game's compatibility certification.
Extended run separately verified that a newly restricted device pair continues to discover permitted UDP port 19021, does not discover unapproved-for-pair group port 19022, and ICMP is denied while another peer stays available. Restored ACL restored both responders. Incompatible subnet/exit requests rejected. Final extended script was not yet confirmed complete at the time of this commit; do not claim mode-transition reconnection or full extended suite passed.
Two earlier extended attempts exposed test limitations: changes to policy and rolling leases recreate the virtual interface; sockets bound to old interface indexes and multicast memberships need rebinding, and counters reset on rebuild. The fixture now rebinds after policy changes and treats counters as per-generation. Real games may require restarting/rejoining; seamless live switching and stable virtual interface across lease renewals remain outstanding.
Go tests passed including deterministic MAC/prefix checks, ARP ownership, unknown target, forged inner source/MAC, member and service ACL, group TTL and rate/fanout checks. Linux Agent/server and additional Agent targets Windows amd64, macOS amd64/arm64, Linux arm64 compile; Vue build and Web JS syntax pass.

Reproduce with the established Linux root/TUN/network namespace tooling:
```sh
mkdir -p bin
go build -o bin/network-ex-server ./cmd/server
CGO_ENABLED=0 go build -o bin/network-ex-agent ./cmd/agent
sudo bash scripts/m7b-ethernet.sh outside "$(pwd)/bin"
```
No public Internet deployment, native desktop packages or release. Remaining: stable interface across policy/lease updates, actual game compatibility, cross-platform Ethernet/IPv6, broader Ethernet protocol support only after security review, and prior M4/M5/M6 production gates. M8 mobile development can start independently.
